task-preflight — 任务预检

每次收到新任务(不是同一任务的追问/继续)时,在动手前依次完成以下两步,再开始干活。

第一步:判断任务类型,推荐模型/模式

先用一句话说明"本任务属于 X 类",再按下表给出推荐。模型/模式只能由用户手动切换(/model、/fast、Shift+Tab 进 plan mode),所以只推荐,如果当前档位已合适就明说"保持当前即可",不合适就给出建议并等用户表态(切换或说"不切")后再继续。

任务类型典型特征推荐
快问快答 / 查资料只要答案不改代码,或一眼能答Haiku(省额度)或保持当前,直接答
机械小改文案/颜色/一两个文件的小 fix,方案明确fast mode(/fast)或 Sonnet
常规功能开发需求清楚,单模块,改动可预估Sonnet 或保持当前
复杂排查 / 大重构 / 跨模块根因不明、影响面大、要读很多代码Opus / Fable(最高档)
需求还没想清楚 / 大方案设计要先讨论"做什么、怎么做"先进 plan mode,模型用高档

判断拿不准时往高档推荐(宁可多花一点,别用低档硬做复杂任务)。

第二步:执行开工前确认(按全局 CLAUDE.md 既有约定)

  1. 任务来源:任务落在公司项目 git 仓库里 → 先问"这个任务是从哪里来的"(需求单 / bug 单 / 组长 / 产品 / 用户自己的想法)。未经组长或产品背书的改动只能停在草稿分支,不合 sit、不提 PR。个人仓库(如 documents)可跳过背书,但仍确认一下范围边界。
  2. 排查类 or 改动类:用户说"排查/看看什么问题" → deliverable 是排查报告,确认根因前不动代码。
  3. 分支基线:要改代码的任务先 git branch --show-current 核对当前分支;新需求必从最新 master 开新 feature 分支,绝不在别的功能分支上叠加。
  4. 范围复述:一两句复述任务范围(改哪些、不改哪些),有歧义就问,没歧义就直接开工。

输出格式

两步合并成一小段回复,例如:

本任务属于「复杂排查」,建议 /model 切到 Opus(当前是 Sonnet)。另外确认一下:这个任务来源是?(bug 单 / 组长安排 / 你自己发现)当前分支 feature/xxx,基线没问题。

用户回应后(或个人仓库小任务确认无歧义后)进入正式执行。
